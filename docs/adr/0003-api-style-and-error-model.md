# ADR 0003: Стиль API, статус-коди та єдина модель помилок (Error Model)

## Статус
Прийнято (Accepted)

## Дата
2026-10-18

## Контекст
При розробці RESTful API для «DocuFlow» клієнтам (веб-інтерфейсу, зовнішнім інтеграціям) необхідні передбачувані та стандартизовані контракти взаємодії:
- Однакове використання HTTP методів для CRUD-операцій.
- Консистентні статус-коди HTTP.
- Уніфікований формат відповідей при помилках валідації або внутрішніх збоях.
- Сувора відповідність коду описаній OpenAPI/Swagger специфікації.

## Рішення

### 1. Архітектурний стиль API: RESTful over HTTP/JSON
- Використовуються стандартні ресурси у множині (наприклад, `/pages`, `/pages/{id}`).
- Тип передачі даних: `application/json`.
- Операції відповідають семантиці HTTP-дієслів:
  - `POST /pages` — створення нової сторінки (статус `201 Created`).
  - `GET /pages` — отримання списку сторінок (статус `200 OK`).
  - `GET /pages/{id}` — отримання деталей однієї сторінки (статус `200 OK` або `404 Not Found`).
  - `PUT /pages/{id}` (або `PATCH`) — повне/часткове оновлення сторінки (статус `200 OK`, `400 Bad Request`, `404 Not Found`).
  - `DELETE /pages/{id}` — видалення сторінки (статус `204 No Content` або `404 Not Found`).
  - `GET /health` — системний health-check (статус `200 OK`, повертає `{ "status": "ok" }`).

### 2. Єдиний формат помилки (`ErrorResponse`)
Усі помилки повертаються з відповідним HTTP кодом (4xx, 5xx) та єдиним форматом тіла JSON:

```json
{
  "error": "ValidationError",
  "code": "TITLE_REQUIRED",
  "details": [
    {
      "field": "title",
      "message": "Title is required and cannot be empty"
    }
  ]
}
```

#### Поля структури `ErrorResponse`:
- `error` (`string`, обов'язкове) — категорія / тип помилки (наприклад, `ValidationError`, `NotFoundError`, `ConflictError`, `InternalServerError`).
- `code` (`string`, обов'язкове) — машиночитаний унікальний код помилки у форматі `UPPER_SNAKE_CASE` (наприклад, `TITLE_REQUIRED`, `PAGE_NOT_FOUND`, `INVALID_ID`, `INTERNAL_SERVER_ERROR`).
- `details` (`array of objects`, опціональне/рекомендоване) — масив із деталями конкретних порушень або повідомленнями для користувача/фронтенду:
  - `field`: назва поля DTO (якщо помилка стосується поля).
  - `message`: зрозуміле повідомлення про причину помилки.

### 3. Політика HTTP статус-кодів
| Код | Призначення | Тіло відповіді |
|:---|:---|:---|
| **200 OK** | Успішне читання або оновлення | JSON об'єкт ресурсу або список |
| **201 Created** | Успішне створення нового ресурсу | JSON створеного об'єкта |
| **204 No Content** | Успішне видалення ресурсу | Порожнє тіло |
| **400 Bad Request** | Помилка валідації DTO або некоректні параметри | `ErrorResponse` (код `ValidationError` / `INVALID_PAYLOAD`) |
| **404 Not Found** | Запитуваний ресурс не існує | `ErrorResponse` (код `PAGE_NOT_FOUND`) |
| **500 Internal Server Error** | Непередбачена системна помилка | `ErrorResponse` (код `INTERNAL_SERVER_ERROR`) |

### 4. Вимога відповідності OpenAPI
Специфікація API є первинним контрактом (Contract-First approach):
- Контракт публікується у файлі `docs/api/openapi.yaml`.
- Усі роути, формати полів DTO, коди відповідей та схема `ErrorResponse` у коді бекенду зобов'язані строго відповідати `openapi.yaml`.
- Зміни в API спочатку вносяться в контракт, після чого відображаються в коді.
