# Звіт про виконання Практичної роботи №4
**Тема:** Мікросервіси — вибір стилю, контракт API (OpenAPI/Swagger Editor) та базовий CRUD  
**Проєкт:** DocuFlow (Notion Clone) — платформа для ведення бази знань, регламентів та документів  
**Контекст:** Document & Page Management  

---

## 1. Мета роботи
- Прийняти та формалізувати усвідомлене архітектурне рішення щодо стилю системи (модульний моноліт чи мікросервіси).
- Спроєктувати та зафіксувати контракт API у форматі OpenAPI 3.0 (`openapi.yaml`) за підходом Contract-First.
- Реалізувати повний базовий CRUD для ключової сутності обраного контексту (`Page` / Сторінка документа).
- Впровадити шарову архітектуру (`api/`, `service/`, `domain/`, `repository/`) із суворою ізоляцією відповідальностей.
- Зафіксувати архітектурні домовленості через серію ADR (Architectural Decision Records).
- Покрити бізнес-логіку сервісного рівня юніт-тестами (успішні та помилкові сценарії).

---

## 2. Прийняті архітектурні рішення (ADR)

1. **[ADR 0001: Вибір архітектурного стилю — Модульний моноліт](../adr/0001-architecture-style.md)**
   - **Рішення:** Обрано **модульний моноліт** (Modular Monolith) на поточному етапі розвитку продукту.
   - **Обґрунтування:** Проєкт знаходиться на початковій стадії розробки з невеликою командою. Модульний моноліт мінімізує інфраструктурні накладні витрати (немає складнощів розподілених транзакцій, мережевих збоїв IPC, складної оркестрації), зберігаючи високу швидкість ітерацій та чіткі межі між бізнес-модулями через інкапсуляцію за доменами.

2. **[ADR 0002: Шарова архітектура модульного моноліту (Layered Architecture)](../adr/0002-layered-architecture.md)**
   - **Рішення:** Впроваджено 4-шарову структуру:
     - `api/`: Express-контролери, маршрути, отримання запитів, DTO, повернення статус-кодів.
     - `service/`: сценарії використання (Use Cases), валідація бізнес-правил, мапінг DTO <-> Domain.
     - `domain/`: чисті сутності та агрегати (`Page`, `Block`, `User`) без зовнішніх залежностей від фреймворків чи БД.
     - `repository/`: доступ до бази даних PostgreSQL із підтримкою in-memory fallback режиму для тестів.
   - **Заборонені зв'язки:** шар `api/` не має права звертатися напряму до бази даних чи репозиторіїв; уся бізнес-логіка зосереджена виключно в `service/`.

3. **[ADR 0003: Стиль API, статус-коди та єдина модель помилок](../adr/0003-api-style-and-error-model.md)**
   - Зафіксовано стиль RESTful over HTTP/JSON.
   - Встановлено стандартну політику статус-кодів (200, 201, 204, 400, 404, 500).
   - Затверджено єдину схему помилок `ErrorResponse` (`error`, `code`, `details`).

## 3. Контракт API (OpenAPI 3.0)

Специфікацію розроблено у файлі [`docs/api/openapi.yaml`](../api/openapi.yaml) та валідовано у Swagger Editor.

### Спроєктовані маршрути:
- `GET /health` — системний health-check сервера (`200 OK`).
- `POST /pages` — створення нової сторінки (`201 Created`, `400 Bad Request`).
- `GET /pages` — отримання списку сторінок із можливістю фільтрації за `isArchived` та `parentId` (`200 OK`).
- `GET /pages/{id}` — отримання деталей сторінки за її числовим ідентифікатором (`200 OK`, `404 Not Found`).
- `PUT /pages/{id}` — оновлення заголовка, іконки, батьківської сторінки чи архівації (`200 OK`, `400 Bad Request`, `404 Not Found`).
- `DELETE /pages/{id}` — видалення сторінки (`204 No Content`, `404 Not Found`).

## 4. Реалізація CRUD у коді

1. **Доменний шар (`backend/domain/`):**
   - Сутність [`Page.js`](../../backend/domain/Page.js) інкапсулює стан сторінки, валідацію назви, методи `rename()`, `archive()`, `restore()`, управління списком контентних блоків `addBlock()`, `removeBlock()`.
   - Сутності [`Block.js`](../../backend/domain/Block.js) та [`User.js`](../../backend/domain/User.js).

2. **Рівень сховища даних (`backend/repository/`):**
   - [`PageRepository.js`](../../backend/repository/PageRepository.js): реалізує CRUD-операції з PostgreSQL через параметризовані SQL-запити до таблиці `pages`, а також автоматичний fallback на роботу в оперативній пам'яті (`useMemory: true`), якщо сервер БД недоступний.

3. **Сервісний рівень (`backend/service/`):**
   - [`PageService.js`](../../backend/service/PageService.js):
     - `createPage(dto)`: валідує наявність заголовка, обмеження довжини (1-255 символів), перевіряє існування `parentId`.
     - `listPages(filters)`: фільтрує сторінки за архівацією та батьківським ID.
     - `getPageById(id)`: валідує формат числового ID, викидає `NotFoundError` (404), якщо сторінку не знайдено.
     - `updatePage(id, dto)`: запобігає встановленню сторінки батьком самої себе (`CIRCULAR_PARENT`), валідує поля.
     - `deletePage(id)`: видаляє сторінку після перевірки існування.
     - Мапінг `toDTO(page)`: трансформує внутрішній стан сутності у вихідний DTO-контракт.

4. **API рівень (`backend/api/`):**
   - [`pageRouter.js`](../../backend/api/pageRouter.js): маршрутизує запити, делегує виконання `PageService`, передає помилки в централізований `errorHandler`.

## 5. Тестування

Створено два набори тестів за допомогою вбудованого тест-раннера Node.js (`node:test`):

1. **Юніт-тести рівня `service/` ([`backend/test/service.test.js`](../../backend/test/service.test.js)):**
   - Створення сторінки: успішний випадок з коректними даними; помилковий випадок (порожній title -> `ValidationError`); неіснуючий `parentId` -> `NotFoundError`.
   - Отримання сторінки: успішний випадок пошуку; неіснуючий ID -> `NotFoundError` (404); невалідний формат ID -> `ValidationError` (400).
   - Оновлення сторінки: успішний випадок оновлення полів; спроба встановити сторінку батьком для себе -> `ValidationError`.
   - Видалення сторінки: перевірка видалення та подальша недоступність ресурсу.

2. **Інтеграційні тести API ([`backend/test/api.test.js`](../../backend/test/api.test.js)):**
   - Перевірка повної відповідності HTTP-ендпоінтів специфікації OpenAPI.
